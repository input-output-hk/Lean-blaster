InstKey packing (e57c853): platform assumptions
-----------------------------------------------
Key = (addr >>> 3) ||| (offset <<< 49). The fast path applies when offset < 2^13.
Otherwise the key is built as a Nat bignum with the same layout.
This assumes:
  1. 64-bit USize. On a 32-bit target, `offset <<< 49` on USize shifts mod 32,
     which breaks injectivity.
  2. Objects are 8-byte aligned. This holds for Lean's allocator.
  3. User-space addresses are below 2^52. Nothing checks this at runtime.
     It can be broken by x86-64 LA57 with high mmap hints, aarch64 52-bit VA,
     or top-byte pointer tags (TBI/MTE, e.g. Android heap tagging).
If any assumption fails, keys collide silently. A cached instantiation for
another subterm could then be returned, which means a wrong translation and
possibly an unsound Valid. Suggested hardening (not done): if addr >= 2^52, use
the bignum path with the offset at bit 64.
TestsSolver/InstKeyPacking.lean has #guard checks for injectivity in the
supported range and for the old collision.
