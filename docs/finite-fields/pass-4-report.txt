Correction to pass 3
--------------------
Pass 3 claimed step 1 complete, and listed as a display-only limitation
that cvc5 values of function-typed datatype fields "are unreliable". That
was wrong: Blaster displayed false counterexample values without saying so.
Reproduced on 9d568b5:
  ∀ (s : FunBox) (x : Int), s.fn x = x        (FunBox: fn : Int → Int, k : Int)
  displayed  s: P.FunBox.mk (P.FunBox.mk.0 $0) 1
The displayed value refers to s itself, with no warning. cvc5 printed
"Could not evaluate (P.FunBox.mk (P.FunBox.mk.0 $0) 1) in getValue" on
stderr. Option (Int → Int), (Int → Int) × Int and structures with two
function fields showed the same problem. Closed values can be wrong too.
Manual probe, same model, for ∀ (s : Outer) (x : Int), s.inner.fn x = x + s.b:
  (get-value ($0))                          -> (Outer.mk (FunBox.mk (lambda .. 0) 0) 0)
  (get-value ((FunBox.mk.1 (Outer.mk.0 $0)))) -> 1      (contradicts inner.k = 0)
Requesting the selector term at function sort was consistent in every probe:
  (get-value ((FunBox.mk.0 $0)))            -> (lambda ((B Int)) (ite (= B 2) 6 (ite (= B 1) 5 0)))
  (get-value ((@ (FunBox.mk.0 $0) 1) ...))  -> 5, 6, 0, as the lambda gives.

Fix (cvc5 only; z3, defaults and verdicts untouched)
----------------------------------------------------
- ModelSchema (Blaster/Smt/Term.lean) is built from the canonical commands.
  It holds the constant sorts, datatype declarations (parametric ones are
  instantiated), define-sort aliases, and the declared/defined symbol names.
- retrieveTypedValue (Blaster/Smt/Env.lean) handles each cvc5 counterexample
  variable whose sort can hold function values:
    * datatype holding function values: the constructor comes from
      (get-value (t)). It is confirmed with (get-value ((is-C t))) when the
      sort has several constructors. Each field is then retrieved
      recursively through (get-value ((sel t))), at the field's sort. The
      fields inside the outer value are never used;
    * function value: (get-value (t)) at its own function sort;
    * other leaves: (get-value (t)).
  Every leaf must be closed: it must not refer to a declared or defined
  constant or function. A function value that contains constructors of
  datatypes holding function values is rejected (e.g. f : Int → FunBox,
  where cvc5's lambda contains (FunBox.mk (FunBox.mk.0 ($0 1)) ...)). A
  budget of 256 get-value requests applies per variable.
- Any failure: the variable shows `<counterexample unavailable>` and the
  existing warning "Counterexample unavailable from cvc5; the Falsified
  verdict is preserved. <var>: <reason>; raw value: <raw>" is logged. The
  status is modelFailed, as before. The verdict cannot change, and agree
  mode saves agreement artifacts. Nothing is invented or guessed.
- z3, and cvc5 variables of first-order sorts, still use the previous
  single get-value path. evalTermFor was refactored to share requestValue,
  with identical messages.

Higher-order rendering and replay review
----------------------------------------
- The selector, tester and function-sort get-value requests go through
  renderFor like every other command. Only `select` becomes `@` and `Array`
  becomes `->`, so z3 text is unchanged.
- No get-value request can be the first function-valued command: an Array
  sort in a datatype field or a constant sort switches cvc5 to HO_ALL at
  declaration time (SmtCommand.usesFunctionValues). This holds for
  parametric instances too, e.g. (declare-const $0 (@Option (Array Int Int))).
- enableHigherOrder stores the triggering command before the respawn. The
  replay therefore contains it, and the replayed session is skipped in the
  broadcast loop, so the command is not sent twice. Sessions that are
  respawned later (first mode) use the stored HO setup. #bmc through the
  mid-query switch is exercised live in single, first and agree modes. No
  defect was found, and nothing else was changed.

Status and remaining limits
---------------------------
Step 1 is complete for model retrieval in this sense: cvc5 counterexample
values of function and function-holding datatype sorts are either requested
at their own sorts and checked to be closed, or explicitly reported as
unavailable with the raw value. No known-wrong value is displayed silently.
Remaining limits:
- Function values whose codomain (or domain) holds datatypes with function
  fields, e.g. f : Int → FunBox: cvc5 gives no usable value. The evidence is
  explicitly unavailable for cvc5. In first and agree modes, z3's value is
  shown when z3 provides it.
- The leaf function values are cvc5's own lambdas for function-sorted
  terms. They were consistent in every probe and are checked at the points
  the tests use, but Blaster cannot verify them in general.
- In agree mode the displayed counterexample is z3's when both are
  complete (existing tie-break). cvc5's typed values appear only in the
  level-3 diagnostics and in agreement artifacts.
- Goals without top-level variables still fall back to a raw (get-model)
  dump, which is labeled raw and is not type-directed.
- Under HO_ALL, cvc5 can be Undetermined on goals that mix function values
  with recursive datatypes (e.g. a List (Int → Int) goal is Undetermined in
  10 s), so type-directed retrieval through recursive datatypes is covered
  by the pure schema tests only, not live.
- Finite-field translation itself is later work (not started).
